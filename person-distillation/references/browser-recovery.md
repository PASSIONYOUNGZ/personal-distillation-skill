# 浏览器接入、慢页面和人工交互

在首次浏览器调用前读本页。使用宿主当场给出的工具说明；以下是决策，不是绕过工具限制的控制接口。

## 先判断故障在哪一层

| 证据 | 可作的结论 | Agent的下一步 |
| --- | --- | --- |
| 清单里没有外部Chrome | 本对话尚未暴露该连接，原因待核 | 进入下方扩展通信诊断，不只重复清单或@请求；不诊断成Chrome不支持或X未登录 |
| 开页调用超时，但标签已有正确标题/URL | 创建可能成功，读取未完成 | 复用原标签，给慢页面一次合理的读取预算；不再创建相同页面 |
| AX读取慢而DOM可读 | 观察方式延迟不同 | 使用已文档化的DOM局部读取；不要求重新登录 |
| 一个站超时，浏览器清单正常 | 该页/该观察方式未知 | 必要时用另一已知相关页面作一次对照，不推断所有平台都坏了 |
| 实际显示登录/验证码/权限提示并挡住所需内容 | 有具体人工动作 | 给浏览器、URL、操作和影响；集中一次处理 |
| 静态搜索抽取空白、403/412 | 该抽取方式受限 | 用正常渲染页验证，不能把搜索失败冒充原生浏览器失败 |

工具名清单未单列浏览器接口时，先检查宿主是否提供正式Browser运行时及Node REPL初始化说明，按公开接口列出实际浏览器；不要直接把Windows桌面控制的URL检查失败当成Chrome扩展也不可用。两条连接分别判断，使用正式连接及其安全检查，不用私有控制协议替代。

## 有界恢复

1. 先查实际浏览器及标签清单。复用目标页面；不要盲选第一个标签或把mcpapps当社交浏览器。
2. 慢社交页面用单步调用，外层工具允许时设约60秒执行预算，内部读取/定位预算须小于外层；不把多个可能各耗时30秒的动作塞进同一个60秒调用。正常接口不人为sleep，不等待networkidle作为动态站通用条件。
3. 超时后查标签是否已创建/导航完成。会话仍在就复用；内核重置则按工具初始化规则重新绑定已有标签。最多一次恢复观察；使用文档支持的DOM快照/局部文字/截图回答下一问题，不反复全量AX。若有明确进展可继续，连续无进展约3分钟停该恢复循环。
4. 留操作、观察方式、预算、实际耗时、结果、tab/session、证据和下一动作。超时不等于登录失效，累计调用耗时不等于网页加载耗时。一个站失败不把其他未测来源写成同样失败。
5. 恢复仍无结果，记tool_timeout/connection_unverified及已试路径；只有已确认的人工动作才交用户。平台天然目录缺口与工具故障分开，研究期间继续核正常替代及范围边界。

## X外部连接

X原生浏览器与登录从首次走外部浏览器。已列出连接时Agent自行选择并打开目标页，沿用登录。未列出时先按现有连接工具/可用插件诊断；如宿主提供插件搜索可搜索一次，空结果只代表本次搜索未返回，不能证明没有接入方式。

Codex/ChatGPT桌面的标准方法是官方浏览器扩展。依据[官方浏览器扩展说明](https://learn.chatgpt.com/docs/chrome-extension)，用户可在当前对话用@选择Chrome或目标标签；若不存在，检查Settings → Computer Use中浏览器是Manage还是Install、是否开启菜单开关、是否为安装扩展的同一浏览器个人资料。菜单可能因版本变化，以当前官方说明/实际界面为准。常规连接修复可沿现有授权执行；涉及用户操作或新的安全敏感权限按宿主规则交接。不要直接重装、关所有标签、重启整个应用或索取Cookie。必要时新对话重试是官方恢复分支，不是每次调用要求。

向用户只提出已查明的下一步。尚未选浏览器时可请其@选择；用户已经@并打开目标页后，不再把同一步作为答案，也不只让其反复查看Manage/Install。Manage、@菜单可选、扩展在浏览器中启用、实际通信成功是不同状态。公开单帖HTTP仍是独立路线，但不证明最新目录。

### 扩展通信诊断：先核链路再交接

若用户已选外部浏览器而清单仍无连接，读取当前宿主浏览器插件提供的故障排查文档。优先使用随该插件提供的只读诊断，而非自行扫描浏览器数据。若提供以下脚本，可从实际插件根目录用当前可用Node执行（版本、路径、扩展ID由宿主提供，不写死维护者环境）：

```text
node scripts/chrome-is-running.js --browser chrome --json
node scripts/installed-browsers.js --json
node scripts/check-extension-installed.js --browser chrome --json
node scripts/check-native-host-manifest.js --browser chrome --json
```

选择Edge时按实际文档换browser参数。没有这些脚本/运行时就用宿主官方设置诊断，不为一次检测安装整套开发环境。仅保留浏览器运行、选中个人资料、扩展安装/启用、原生通信注册和错误类别；不读取或保存Cookie、登录凭据、浏览历史、完整Preferences。扩展管理页/商店URL从插件提供的配置或当前官方文档取得，不猜ID。

**检查诊断执行环境。** Windows沙箱可能把LOCALAPPDATA、HKCU和进程清单隔离：路径落在sandbox配置、tasklist权限/身份错误、只在沙箱报注册缺失，都不能当真实用户的扩展缺失。按宿主批准机制运行官方只读诊断于真实用户上下文；未获准时明确“未能检查真实配置”，不可改注册表或用私有控制通道绕过。终端看不到进程不证明用户没开浏览器。

按结果采取单一动作：

- 扩展installed=true、enabled=false：请求用户在**实际选中个人资料**的扩展管理页启用指定扩展，已有站点登录沿用。@和重启对话不会启用被禁用的扩展。若是组织策略禁用，不覆盖策略。
- 浏览器确实未运行：沿用户已授权范围和宿主规定启动，随后复核；不把诊断命令失败当未运行。
- 扩展未安装：给实际官方安装入口，按宿主权限要求处理；不要先要求重新登录站点。
- 原生通信注册缺失/错误：按插件排查文档，通过官方插件UI修复/重装。不得自行运行installManifest、直接改注册表或写原生通信清单。
- 上述检查通过仍断连：按当前官方文档有界重连；涉及关闭应用/浏览器先保留工作并按授权交接。保留已完成动作，失败时给具体诊断和支持回执，不重复发送同一设置清单。

用户完成动作后，只复验受影响的扩展状态、工具清单、同一外部浏览器目标页；实际读取成功才记browser_connected。先前已通过的其他平台不用重登或从头巡检。打开页证明连接/访问，目录增量和完整范围另验。

诊断结果只证明所检查的层。原生通信清单与注册项正确，不代表清单指向的可执行文件存在、版本指向正确或握手成功；按宿主允许的只读诊断核对实际文件与版本。扩展禁用是扩展连接路径的必要条件未满足，不代表启用后必定恢复，也不能排除同时存在宿主路由故障。若扩展已启用、通信文件正确而清单仍未暴露外部浏览器，保留实际错误并转入宿主连接故障分支，不循环要求重登网站。

先确认正在修复哪条路径：当前宿主的扩展浏览器连接、独立自动化浏览器、公开HTTP单帖读取、用户导出是不同能力。历史上后一种成功不能证明当前扩展连接正常，也不能把扩展要求强加给公开HTTP路径。类似问题的网络案例用于形成待验证假设，不把他人的macOS权限修改、关闭沙箱或手写注册项当通用修复。独立自动化只能在宿主明确支持且授权时采用，不能用于绕过当前工具限制，也不假定共享日常浏览器登录。

历史已登录浏览器DOM导出、专用扩展与公开单帖接口是不同路线。旧导出可复用方法和有来源材料，不能推断新的宿主支持旧控制工具；不把未维护的专用扩展硬塞给初次用户。

## 新用户交互

- 工作目录是Agent自动建立的输出位置；作品目录是Agent从作者主页取得的帖子索引。不要混称“目录”让用户准备文件。
- 没有用户提供/确认已有材料，不给“导入你的已有目录/正文”默认选项；纯导入能力保留给用户明确选择的场景。
- 首次集中清单只含具体连接、登录、验证码或确实需要的权限。未知故障继续由Agent诊断，不转交“你选如何恢复”。
- 发现一个动作先记下来，其他必要来源仍在轻探时不发单独异步问句。初探的恢复只为确定人工动作；已可读文章无需在此时深追作者历史、全文和多个入口，避免把集中准备拖成长时间研究。
- 若经过有依据的正常恢复和替代仍无法完成精确范围，再一次说明具体缺口及影响，让用户选择继续等待该条件或调整范围/阶段交付；不能用该选择替代尚未做的恢复。默认保留原请求，不因超时偷偷改30项为任意30条。
- 六平台是来源发现核对清单，不是六个强制登录/深测任务。未发现本人账号可记未发现；不能编URL、创建虚假必要来源。已确认核心来源必须保留，不能因难取改为不重要。

访问故障可能仍需要真实用户连接/验证；Skill不能保证任何环境零人工。验收看是否提出必要、具体、最少的动作，以及是否保留范围事实。
